# Engine notes

Internal operating notes for the EvoTaste engine (`evotaste/` minus the task layer and the verifiers). The scientific design is `docs/design/round-2.md` and, for the amplification mechanisms, `docs/design/amplification.md`; the build contract `docs/dev/ROUND2_SPEC.md`, the vLLM and trainer recipes `docs/dev/INFRA_NOTES.md`. The task layer — sources, suites, the probe set, the training stream and scoring — is described in `docs/dev/ENV_NOTES.md`, the verifiers and the sandbox in `docs/dev/VERIFY_NOTES.md`; the engine uses them only through the contract (`Task`, `Score`, `score_many`, `prompt_ids`, `Streams`, `fixed_tasks`). This file holds the commands and how to launch them on the shared machine, the run-config schema, the mechanisms whose details matter for results, the on-disk layout and record schemas that analysis code is written against, measured costs, and known limitations. Round 1's engine is reproducible from the tag `round-1`.

## Commands

All commands run from the repository root after `source scripts/env.sh`, with exactly one GPU visible (`CUDA_VISIBLE_DEVICES`). The script also sets `PYTHONHASHSEED=0`, which child processes inherit and `evotaste.tasks` requires. Each command that generates text starts its own vLLM server (1–4 minutes with warm compile caches) and stops it on exit; the server also dies if its parent is killed with SIGKILL. `--attach http://127.0.0.1:<port>` uses an already running server of the same model instead (development only; see `scripts/dev/serve_vllm.sh`).

| Step | Command |
|---|---|
| Prepare a run | `python -m evotaste.worker prepare configs/run/<name>.yaml [server overrides]` |
| Fork a run after seeding | `python -m evotaste.worker fork runs/<source> configs/run/<new>.yaml [--dry-run]` |
| Run or resume a worker | `python -m evotaste.worker run runs/<name> --members m00,m01 [--checkpoint-every 5] [server overrides]` |
| Evaluate | `python -m evotaste.evaluate run runs/<name> --suite selection --adapters base,population@60,m00@60 --per-family 50 [--per-source 300] [--samples 2] [--shard i/n] [--tag final] [server overrides]` |
| Harvest | `python -m evotaste.evaluate harvest runs/<name> --tag final [--step S]`, then commit `docs/harvest/<name>.json` |
| Add clones to a run | `python -m evotaste.worker prepare configs/run/<name>.yaml` with the clones appended to its member list, then `worker run` on them |
| Context score | `python -m evotaste.evaluate context-score runs/<name> [--items 120] [--contexts a,b] [--members m00,m01] [--steps 0,45]` (no vLLM; the base model on the visible GPU) |
| Probe scaled adapters | `python -m evotaste.evaluate scaled runs/<name> --adapters m00@45,m01@45 --factors 1.5,2 [server overrides]` |
| Deviation, cross-likelihood | `python -m evotaste.evaluate deviation runs/<name> [--items 120] [--members m00,m01@45x2] [--steps 45] [--cross]` (no vLLM) |

Server overrides are `--kv-cache SIZE`, `--max-loras N` and `--gpu-memory-utilization F` (see Run configuration). Resuming is the same `run` command again. In practice workers and evaluations are started through the scripts below rather than by hand.

## Launching on the shared machine

Other users start 8–30 GiB jobs on every card without warning, including cards our workers use, so no card stays exclusive. Three scripts handle this; each runs from the repository root after `source scripts/env.sh` and keeps its log and control files in `logs/<name>/`.

- `scripts/supervise_run.sh runs/<name>` is the way to train. It keeps every member list of a run alive: on each pass it starts a list that has unfinished members and no live worker on one of the allowed cards with enough free memory, and so restarts workers killed by a co-tenant, elsewhere if need be. It reads, on every pass, `lists` (one comma-separated member list per line, one worker each), `gpus` (allowed indices), `worker-args` (extra `worker run` arguments such as `--checkpoint-every 5 --kv-cache 12G --gpu-memory-utilization 0.45 --max-loras 10`), `need-free-mib` (default 40000) and `upgrade-after` (touch it to have every older worker stopped right after its next checkpoint and restarted on the current code and arguments, losing no steps). Stop it with SIGTERM; workers keep running.
- `scripts/queue_workers.sh runs/<name> m1,m2 m3,m4 …` is a one-shot launcher for a quiet machine: it starts each list on the next completely free card and withdraws a worker whose card another user claims within a minute. It does not restart anything; prefer the supervisor.
- `scripts/run_eval.sh runs/<name> <suite> <tag> <adapters> <per-family> <samples> <per-source> <shards>` runs one evaluation as shards, one per card with at least `NEED_FREE_MIB` (default 21000) free that hosts none of our workers or shards, each with `--kv-cache 12G --gpu-memory-utilization 0.42`; a shard that dies is started again (up to 6 attempts) and the script exits 0 when every shard has finished.

Put a clone in the same member list as its parent: a worker whose only unfinished members are clones waiting for a parent that another worker advances keeps its vLLM server and polls every minute until the parent has committed the clone point.

Every command writes whatever ends it to its own log before it exits: the traceback of an exception (`terminated by an exception`, or `exiting: <message>` for a refusal), or `received SIGTERM` / `received SIGINT` and `stopped by …` for a deliberate stop. Keep stderr (the scripts append it to `stderr-gpu<g>.log`), since an interpreter-level failure before logging starts can only appear there. A worker also logs whether the working tree was clean at launch; if not, it logs the modified files and the SHA-256 of `git diff HEAD` and keeps the diff as `logs/<name>/uncommitted-<hash>.patch`, so a run from uncommitted code can be reconstructed.

## Run configuration

A run config is YAML; unknown keys, missing required keys and wrongly typed values are errors. `prepare` freezes it into `runs/<name>/config.yaml`, with `suites`, `contexts` and `strata.path` pointing at copies placed next to it, and every later command reads only that copy. It also records in `prepared.json` the version of the training stream's batch arithmetic (`stream_version`, described in `docs/dev/ENV_NOTES.md`), which the run keeps for good, clones added later included: version 2 for runs prepared or forked since 26 November, version 1 for those prepared before, whose `prepared.json` has no such key (pilots B, C and D). `configs/run/pilot-template.yaml` writes out the pilot defaults and shows every way a member can start; `configs/run/pilot-d.yaml` sets the undirected amplification mechanisms per member; pilot E, clones at the end of `configs/run/pilot-c.yaml`, the taste-shaped reward; pilot F, clones at the end of both files, revisits; `configs/run/toy.yaml` is a small end-to-end run.

| `amplification.length.free`, `.slope` | 2048, 0.25 | the length deduction of the return (below) |
| `amplification.advantage` | `centered` | `centered` or `standardized` (Round 1's rule, for comparison) |
| `amplification.self_imitation` | 0.0 | β, the weight of the self-imitation term |

| `amplification.practice` | null | `{eta, decay, floor, ceiling, reference?}` (the first four required; eta ≥ 0, 0 ≤ decay < 1, 0 < floor ≤ 1 ≤ ceiling; `reference: base` tracks the gain over the base model): self-chosen practice |
| `amplification.taste` | null | `{strength, clip?, residualize?}` (clip default 2; clip > 0 and \|strength\| · clip < 1, so that a correct answer keeps a positive reward; strength may be negative; `residualize: true` shapes on the score's residual after its fit on log length): the taste-shaped reward; strength 0 is exactly the update without it |
| `amplification.revisit` | null | `{share, source, min_seen?, imitate?}` (0 ≤ share ≤ 1; source `own` or `matched`; min_seen default 4, at least 1; imitate default 0, at least 0; not together with `practice`): consolidating one's own frontier; share 0 keeps the item record and the shared batch |
| `probes.every`, `probes.max_tokens` | 15, 4096 | probe and checkpoint every E steps and after the last step; the limit is also used by `evaluate` |
| `culling.enabled` | true | false: would-be culls are recorded and logged, nobody is culled or replaced |
| `culling.grace`, `culling.max_replacements` | 40, 2 | no culling at probes before this step; new lineages per slot before the slot is given up |
| `clonable_steps` | none | steps at which every member keeps its checkpoint with optimizer state, so that clones can be added later |
| `members` | required | list of `{id, seed, context?, parent?, overrides?, role?}` |

A member id uses letters, digits, `_` and `-`. `seed` is the lineage seed (LoRA initialisation, every sampling seed, imitation draws); seeds must be distinct within a run, since two members with one seed would share their initialisation and draw with common random numbers, which makes unrelated members look alike. `context` names an entry of the contexts file (`placebo`, a stance or a tactic); it is required for seeding by `opcd` or `imitation` and forbidden for `none`. `role` is `member` (the default, a population member) or `baseline` (trains, probes and evaluates like a member but is never ranked). `overrides` may replace keys of `seeding`, `amplification` and `culling` for one member; nested sections such as `length` are merged key by key. A member with `amplification: {steps: 0}` stops after seeding and its step-0 probe.

`parent: {member, step}` makes a member a clone: it starts from that member's checkpoint at that step and continues it (see Members). The parent may itself be a clone; the chain must end at a seeded member, without cycles. A clone takes its parent's context and effective settings, with its own `amplification` and `culling` overrides on top, so along a chain each clone inherits what its parent had; it may not set `context` or seeding overrides, and the step must lie within the parent's course (from the parent's own start to its last step) and below the clone's own `amplification.steps`. A clone after step 0 must keep its parent's `practice` settings, since it continues the parent's practice record; at step 0, where nothing has been recorded, it may set them freely. It may set `taste`, which keeps no state: pilot E clones members of pilot C at step 45 into strength +0.25, 0 and −0.25. It may set `revisit`, whose item record it inherits from a parent that keeps one and otherwise rebuilds from the recorded rollouts: pilot F clones pilot D's three relative-only members and pilot C's `placebo-adv` at step 45 into revisits of their own frontier (`-fro`), matched revisits (`-mat`) and plain training (`-pln`).

Clones can be added to a run after it has started, or after their parents have finished: append them to the member list and run `prepare` on the extended config. `prepare` accepts a config that differs from the frozen one only by clones appended at the end, provided each clone's parent keeps that checkpoint with its optimizer state by the frozen config (one of its clone points, a `clonable_steps` entry, or step 0 of a seeded member) or is appended with it; it records the extension in `prepared.json`, and `worker run` on the new clones starts them without touching any other member. So a run whose clone points are chosen later lists those steps in `clonable_steps` from the start (pilot C: `[45]`).

Launch-time settings do not alter the frozen run and never change results. `--kv-cache`, `--max-loras` and `--gpu-memory-utilization` replace the `server` keys for one process (`worker run`, `worker prepare`, `evaluate run`; logged at start); `--checkpoint-every` is described under Resilience. Measured vLLM footprints for Qwen3-1.7B at rank 32 are about the KV budget plus 6.8 GiB (26.8 GiB at 20G, 18.9 GiB at 12G, about 14.9 GiB at 8G; two more LoRA slots add about 0.15 GiB); the trainer's peak is in Measured costs. Lower `--gpu-memory-utilization` with the KV budget (about 0.45 at 12G, 0.35 at 8G), or vLLM's startup check fails beside a co-tenant. Nothing else sizes itself from the KV budget: the client keeps up to 512 requests in flight and the trainer's token budget is independent; a small cache only makes vLLM pause and recompute sequences when answers are long, which at 4,096 tokens happens often (a 12G cache holds about 112k tokens, some 25 full-length sequences).

## Members

A member starts in one of two ways.

**Seeding** (every non-clone member). The LoRA tensors are drawn from the lineage seed with B = 0, so the member starts as the base model; then `seeding.steps` updates, each on `seeding.batch` prompts of `Streams.seed_batch(i, batch, domains)`, the same prompts for every member with the same batch and domains:

- `opcd`: the member samples one completion per prompt behind its own prompt (no context), the trainer re-scores a sample of them (the consistency check below), and one AdamW step minimises the token-mean reverse KL over completion tokens, Σᵢ Σₜ KL(π(·|xᵢ, yᵢ<ₜ) ‖ base(·|cᵢ, yᵢ<ₜ)) / Σᵢ |yᵢ|, where xᵢ is the member's prompt, cᵢ the prompt that carries the context (the context text, framed by the file's preamble and closing, appended to the system prompt by `prompt_ids(..., context=...)`), yᵢ the member's own sample, and `base` the frozen base model: the same network with the adapter disabled and no gradient. The KL is over the full vocabulary at every completion position; the gradient does not flow through the choice of the sampled tokens (as in on-policy distillation generally). The new weights are published before the next update's sampling. The KL of every update is logged.
- `imitation` (Round 1's method with a context): the base model answers each prompt `seeding.samples` times behind the prompt that carries the context; the correct, stopped answers form the update's pool, and `batch` sequences are drawn from it with the lineage seed (a prompt with a correct answer uniformly, then one of its correct answers) for one positive update behind the member's own prompt. An update without any correct answer stops the worker.
- `none`: no update; the unseeded control.

All new members of a worker seed in lockstep: round i makes update i of every member that has one, with one joint generation. Amplification then starts from a fresh AdamW state, after the step-0 probe and checkpoint.

**Cloning.** A clone waits until its parent (the parent slot's first lineage) has committed the clone point, then loads the parent's checkpoint at that step, fp32 adapter, AdamW state, practice record and item record (or rebuilds the item record, see "Consolidating one's own frontier"), takes the parent's step counter, probes at that step with its own seed, commits its own copy of the checkpoint, and continues on the shared training stream: the same prompts as its parent and siblings at each step, different sampling seeds. A practising clone draws its batches from the inherited record, so at the clone point it gets exactly its parent's batch, and its prompts diverge from its siblings' only as their records do. Because the parent's state is copied exactly, two clones of one parent and step differ only in their sampling seeds (and in vLLM's batch-dependent numerics), and so does a clone from its parent's continuation. A parent writes a checkpoint at every clone point that a member spec names (a light one if it is not a probe step) and keeps its optimizer state; a parent culled before the clone point makes the clone's worker stop with an error. Clones at step 0 of a seeded member that has no amplification steps of its own are how the template trains one seeded state under both update rules: both rules start from byte-identical weights and see identical prompts, and either can be cloned again later.

**Sampling seeds.** Every request carries an explicit seed, so that two lineages differ by construction and a rerun is as reproducible as vLLM allows (its draws are a function of seed and position, but batch composition changes bf16 numerics). Seeds are `stable_seed(tag, …)` of: `("opcd", lineage seed, update, prompt index)` and `("imitation", …)` for seeding; `("rollout", lineage seed, step, prompt index)` for amplification (vLLM gives the k-th of n samples seed + k); `("probe", lineage seed, step, item index)` for probes, scaled probes of that lineage's step-`step` adapter included; `("probe", "base")` and `("probe", "base", context)` plus the item index for the base model's reference answers; and `("eval", adapter content hash or "base", uid)` for evaluation, the same in every shard and under any label of the same adapter. A replacement lineage after a cull gets the seed `stable_seed("lineage", slot seed, k)`.

## Returns, advantages and the update

The reward is the task layer's (`Score.reward`: 1 iff the answer is in the wrapper asked for, verified correct, and the completion stopped); with the taste-shaped reward (next section) that of a correct, eligible rollout is first multiplied by its factor. The return adds the length slope: `return = reward − slope · clip((tokens − free) / (max_tokens − free), 0, 1)`, with `tokens` the completion's sampled ids (end-of-turn included), so nothing is deducted up to 2,048 tokens and 0.25 at the limit. With `centered` advantages a rollout's weight is (return − group mean) / 0.5; a group whose returns are all equal gets exactly zero, and a length difference alone gives weights proportional to it (two otherwise equal answers of 2,560 and 3,072 tokens: about ±0.06). Dividing by the group's spread instead (`standardized`) would make any such difference a full-size signal. Records, probes, culling and evaluation stay on the binary reward; only the update sees returns.

One AdamW step with gradient clipping minimises the sum of up to four terms over the step's batch, each normalised by its own token count:

  −Σ_{i: wᵢ≠0} wᵢ Σₜ log π(yᵢₜ) / Σ_{i: wᵢ≠0} |yᵢ|
  + β · (−Σ_{i∈E} Σₜ log π(yᵢₜ) / Σ_{i∈E} |yᵢ|)
  + λ · Σ_{i∈E} Σₜ KL(qᵢₜ ‖ π(·|xᵢ, yᵢ<ₜ)) / Σ_{i∈E} |yᵢ|,   qᵢₜ = softmax(lᵢₜ + γ (lᵢₜ − bᵢₜ))
  + ρ · (−Σ_{i∈R} Σₜ log π(yᵢₜ) / Σ_{i∈R} |yᵢ|).

The first is the advantage term. The second is self-imitation (β = `self_imitation`). The third is exaggerated self-imitation (`exaggeration: {gamma: γ, weight: λ}`): l and b are the member's and the base model's full-vocabulary logits at the same position of the same prompt and completion, and the target q, the member's own distribution pushed further from the base model's, is computed without gradient, so the gradient with respect to the member's logits is π − q. A member equal to the base model feels no push, and where the member deviates, the term moves it further along its own deviation. E, the rollouts eligible for both imitation terms, are those with reward 1, whatever their advantage, and with `imitate_within_free: true` only those of at most `length.free` completion tokens, because imitating every success amplified length in pilot C. The fourth is replay imitation (ρ = `revisit.imitate`): R holds the stored first successful answers of the step's revisited items, which take part in no other term (see "Consolidating one's own frontier"). A term whose weight is 0, or the exaggeration with γ = 0 (whose target is the member itself), is not computed at all, so the update is then exactly the one without it; a step in which no term has a sequence leaves the weights and the optimizer untouched. The history records each term's loss (`adv_loss`, `si_loss`, `ex_loss`, and `rp_loss` when ρ > 0) and the sequences and tokens it used.

The trainer scores exactly the sampled token ids behind exactly the prompt ids sent to vLLM; on GPU its LoRA matmuls run in bf16 like vLLM's, over fp32 master weights. Rows hold a prompt once followed by as many of its completions as fit in `token_budget`, with a mask that lets each completion see only the prompt and itself; a completion that does not fit starts a new row, so at 4,096 tokens most rows hold one completion and memory is bounded by the budget, not by the group. Output projections run only at completion positions, in chunks recomputed in the backward pass: 1,024 positions for sampled-token log-probabilities, 256 for the two full-vocabulary KL terms (distillation and exaggeration), whose chunk holds a few fp32 [256, 151,936] tensors. In the distillation update the teacher's hidden states for a micro-batch are computed first (adapter disabled, no gradient) and only they are kept; the exaggeration term does the same with the base model on the very rows of the member's pass (same ids, positions and mask), keeping only the hidden states that predict eligible tokens, so its target needs one extra forward pass without gradient over the micro-batches that hold an eligible rollout. Each adapter version is saved in bf16 to a new directory under `/dev/shm/evotaste/<run>/<pid>/` and loaded under a new name `<lineage>@<pid>-<counter>`; the previous version is then unloaded and its directory removed, so no request can be served by a stale version.

Before every amplification update and every `opcd` update the worker re-scores part of the samples with the trainer and compares with vLLM's log-probabilities: the first rollout of each prompt, then the second of each, and so on, until at least `check_tokens` completion tokens and `check_rollouts` rollouts are covered (all of them if the batch is smaller). The sample fails if the per-token mean |Δ| exceeds 0.04 or Σ|ΔΣ| / Σ tokens exceeds 0.015; a failed sample is repeated once on all samples of the step (both results logged), and only a failure there stops the worker with `ConsistencyError`. A wrong, stale or swapped adapter shifts every token and fails both, while an isolated bf16 near-tie token (2–3 nats) cannot. Measured in Round 1 with the engine's own code (random adapter, 128 rollouts of up to 640 tokens): 0.0057 and 0.0022 with the right adapter; 0.12 and 0.073 when the base model is served instead of the adapter or the reverse.

## Taste-shaped reward

A member with `taste: {strength, clip}` and strength ≠ 0 changes how much a correct answer earns relative to the other correct answers to the same prompt, by how characteristic of the member it is. Its eligible rollouts are those of the imitation terms: reward 1 (which implies that the completion stopped) and, with `imitate_within_free`, at most `length.free` completion tokens. After the consistency check and before the update, the trainer scores each of them twice without gradient, on the very same prompt and completion ids in the same rows: with the member's weights of this step, which sampled the rollout, and with the adapter disabled. The characteristic score is s = (Σₜ log p_member(yₜ) − Σₜ log p_base(yₜ)) / |y|, the rollout's deviation from the base model in nats per token. In each prompt's group with at least two eligible rollouts, d = s − the group's mean s over them (exactly 0 when their scores are equal); σ is the population standard deviation of all such d in the step; z = clip(d / σ, −clip, clip); and the rollout's reward is multiplied by 1 + strength · z, between 0.5 and 1.5 at strength 0.25 and clip 2. Every other rollout keeps its reward (a wrong one 0, a correct one that is not eligible 1), and so does every rollout of a step with fewer than eight rollouts in such groups or with σ = 0, which the history records as `skipped` (an unseeded member at step 0 is the base model: every score is 0).

With `residualize: true` the score is made length-neutral first: over the rollouts that are shaped (the eligible ones in groups of two or more), s is fitted by least squares as a + b · log(tokens), and those rollouts' scores are replaced by their residuals before d, σ and z are formed. Within a step shaping then cannot follow the part of the score that is linear in log length; the rollout records keep the raw score, the history the fit (`length_intercept`, `length_slope`).

The length deduction and the advantage then apply to the shaped reward as to any other. A group of four correct, short answers, which had no advantage, gets weights strength · (z − mean z) / 0.5; in a mixed group the shaped rewards also move the group mean, and with it the weights of the wrong answers, by a little. Because z is relative within the step, the pressure does not grow as the member moves away from the base model; and since z does not depend on strength, −strength gives factors mirrored around 1 on the same rollouts, which steers toward the base model in a control that differs in nothing else. Recorded rewards, probes, culling and practice averages stay on the scorer's reward; the rollout records keep the shaped `return`, the `taste_score` and the `taste_factor`. With strength 0 nothing is computed and the update is bit for bit the one without the key, so a neutral variant logs no scores; its deviation is measured on its probes (`evaluate deviation`). The member's log-probabilities come from the trainer rather than the sampler so that both terms of s share one code path and one numerics; the history's `member_vs_sampler` gives, over every scored rollout, the consistency check's measure of how far they are from the sampler's.

## Self-chosen practice

A member with `practice: {eta, decay, floor, ceiling}` keeps a practice record: per training source the exponential moving average r_s of its own training reward (the mean reward of the step's rollouts on that source; r_s ← decay · r_s + (1 − decay) · reward, unchanged in a step without the source), all starting at 0.5, near the base model's expected reward per source (0.40–0.49 by the census), and per stream pool the number of items it has drawn. With `reference: base` the tracked value is the gain over the base model instead: the source's mean reward minus the mean of the base model's census pass rates (passes / samples in the pinned strata table) on the items of that source in this step's batch, so that a source's share follows the member's own progress rather than how easy the source is for everyone; the averages then start at 0. Its batch at a step gives source s the share default_s · exp(eta · (r_s − mean r)), where default_s is the source's share of the shared stream (its domain's share split equally among the domain's sources). Clipping to floor..ceiling × default_s and renormalisation are solved jointly, as clip(c · default_s · exp(…)) with c such that the shares sum to one, so that the final shares respect both bounds. Within a source the shares of its sweet, mastered and frontier pools and the 3/20 guardrail-wrapper share of the non-code prompts stay as in the shared stream.

`Streams.member_batch` turns the shares into a batch: each pool's expected count, cut along the cumulative counts at one seeded offset per step, so that every pool's and every source's count is the floor or the ceiling of its expectation and equals it on average (the shared stream's carried remainders would make the batch depend on the member's whole history). Each pool is walked in the shared stream's own permutations, continuing after the items the member has drawn before: without replacement until the pool is exhausted, and only from the train part. The batch is a pure function of (run seed, step, batch size, shares, draws); the offset, the wrapper choices and the order depend on the step alone, not on the lineage, so members with equal records get equal batches and prompts differ between members only through their records. With eta = 0 the member gets the run's shared batch itself, byte for byte, and only its averages are kept. The record is saved with every checkpoint (`practice.json`; JSON floats round-trip exactly), restored on resume and inherited by clones; a checkpoint after step 0 without it is refused. Every history line records the shares the batch was drawn with and the averages they came from.

## Consolidating one's own frontier

A member with `revisit: {share, source, min_seen, imitate}` keeps an item record: for every training item it has been shown, its attempts (rollouts) and successes (the scorer's reward 1, never the shaped reward), the step of its first success and, when that first successful answer had at most `length.free` completion tokens, its sampled ids and the wrapper it was asked under. Every step adds all of its rollouts, revisits included, after the update. The record is saved with every checkpoint (`items.jsonl.gz`), restored on resume, and taken over by a clone: from the parent's checkpoint if the parent keeps one, otherwise rebuilt from the rollout records of the parent and of its own parents up to the clone point (committed steps only; a missing file stops the clone). A rebuilt record has the same counts and first successes as the one the parent would have kept, but no answers, since rollout records keep no sampled ids. Members without the key keep no record, and nothing about them changes.

The member's frontier is the items it has solved at least once but in fewer than 3/4 of at least `min_seen` attempts (default 4, one visit). At each step it takes the run's shared batch and replaces its last n = share · prompts prompts (rounded half up, at least one when share > 0; 16 of 48 at share 0.33) by revisits; candidates exclude every item of the shared batch, so no item is asked twice in a step.

- `own` draws n distinct items of the frontier by successive sampling: each draw takes a remaining item with probability proportional to 1 − its census pass rate + 0.05 (the pinned strata table), so that the items the base model rarely solves come first and none is excluded.
- `matched` makes the draw `own` would make for this member at this step, on its own record, and replaces each drawn item, in draw order, by the item of the same source with the nearest census pass rate among those shown at least `min_seen` times, outside the frontier and not taken yet. The two arms thus revisit equally hard, equally familiar problems and differ only in whether the member's own successes chose them.

Both draws are seeded by (run seed, lineage seed, step), ties of pass rate in a seeded order, so the batch is a pure function of the step and the record and a resumed step draws it again. A slot that finds no item (a short frontier, or no candidate of the source) keeps the shared batch's prompt and is logged as `shortfall`. The non-revisit part of every batch is therefore a prefix of the shared batch at the same positions, and a plain clone sees the whole shared batch: the three arms of a parent see identical stream prompts. Revisits are the stream's own tasks of train-part pool items, with their stratum and the default wrapper (`Streams.train_task` refuses any other uid, so a held-out item can never be revisited), and are ordinary prompts: fresh rollouts, the usual reward, return and advantage. With `imitate` > 0 the update adds the replay term (Returns, advantages and the update) on each revisited item's stored first answer, its own sampled ids behind the prompt it was answered under; items without a stored answer are revisited without it. Revisits cannot be combined with practice, which draws a batch of its own. With share 0 the member keeps its record and trains on exactly the shared batch with exactly the update without the key.

## Probes, culling and the base references

The probe set is the task layer's (`Streams.probe_tasks`: selection items spread over the selection units, plus selection items under held-out wrappers); it is rebuilt by the code at every start, and `prepare`, `fork` and every worker check that it equals, in uid and question, the set the base model answered at prepare time, and stop otherwise. At prepare time the base model answers the probe set plainly (every member's reference) and once behind the prompt of each context in the contexts file (the instructed references of the context score). A probe summary holds the accuracy (mean over families of the family's accuracy), the same by domain, per family, wrapper compliance overall and per wrapper, tolerant correctness (`correct_any`), the truncated share and the mean completion length.

A member is a cull candidate at a probe at step ≥ `grace` (never at step 0) if fewer than half of its probe answers are in the wrapper asked for, more than half are truncated, its probe accuracy is below half the base model's, or its probe accuracy is below the base model's at this probe and at the previous probe at step ≥ `grace`. With culling enabled the lineage is culled and keeps its checkpoints; slot `s` continues with lineage `s~k` (k = 1, 2, …), which starts from scratch (seeding, or for a clone slot a new clone of the same parent point) with seed `stable_seed("lineage", <slot seed>, k)`. With `culling.enabled: false` the reason is recorded in the probe summary with `culled: false`, a warning is logged, and the member carries on.

## Resilience

A worker advances its members until each has finished its steps or its slot is exhausted; killing it at any point and starting the same command again resumes every member from its last checkpoint. Checkpoints are written at every probe, at every clone point of the lineage, and, with `--checkpoint-every N` (default `probes.every`), as light checkpoints without a probe every N steps, so a death costs at most N steps. Resume restores the fp32 adapter, the optimizer state, the practice record and the item record of the checkpoint exactly, discards records of later steps, and continues at the same position of the training stream; it stops if a checkpoint after updates lacks its `optimizer.pt` (for a clone, its parent's updates before the clone point count) rather than silently restarting AdamW, and likewise if a revisiting member's checkpoint after step 0 lacks its item record. Seeding has no checkpoints: a member killed while seeding restarts seeding from scratch, with the same seeds. Several workers can share a run directory with disjoint `--members` lists; an exclusive lock per member slot (`runs/<name>/locks/<slot>.lock`) makes a second worker on the same member exit at once.

A CUDA out-of-memory error in the trainer (a co-tenant took memory on the card) is retried from clean state: cached memory is released, the card's per-process memory is logged, and the same member step (consistency check, update, or seeding update) is tried again every 100 s, up to 10 attempts, before the error ends the worker. A retry computes exactly the update an uninterrupted run would have: the same samples, and the member's weights and a private copy of its optimizer state are copied into the trainer and back only when an update has completed. An error inside vLLM still ends the worker at once, and a final out-of-memory error logs `nvidia-smi`'s per-process GPU memory before vLLM is stopped. A worker limits its torch CPU threads to 4.

## Forking a run after seeding

`fork` creates a prepared run that shares the source run's base references and seeded members. It copies `base/` (the plain and per-context probe answers), and for every member id present in both configs with the same context, seed and effective seeding settings, not a clone in either, whose source lineage has a committed step-0 checkpoint and complete seeding history, it copies that checkpoint (the adapter after seeding, no optimizer state), the seeding history and the step-0 probe, and writes a state at amplification step 0. Other members start normally; clones start from their parents in the new run. It refuses unless model, run seed, `lora`, `seeding`, `probes`, `trainer` and the suites and contexts content are identical; the strata table, amplification, culling, server settings and member overrides of those may differ. The source may be live: files are copied, never moved or linked. `prepared.json` of the fork records `fork: {source, source_revision, members}`, and `--dry-run` prints the plan without creating anything.

## Evaluation and harvest

`evaluate run` evaluates adapters named as `base`, a lineage id (its last checkpoint), `<lineage>@<step>`, or `population@S`, which stands for exactly the labels a harvest at step S ranks (below) and expands the same way in every shard, on the task layer's evaluation set of a part (`fixed_tasks`): `selection`, or the vault `blind2`. It takes `--per-family` instances of every procedural family and `--per-source` items (default the `--per-family` value; at most what the part holds besides the probe set) of every dataset source, both recorded in `params.json`; the default tag `n<per-family>x<samples>` gains `s<per-source>` when they differ. Answers are generated with `probes.max_tokens`. `--shard i/n` splits the (adapter, item) job list; each shard writes its own record file. After each invocation the summary is recomputed over all record files of the tag and written only if every label comes from a single adapter (one content hash across all files) and covers the requested grid exactly, every (family, item, sample) once; while records are only missing (shards still running) the summary is removed with a warning, and any other inconsistency stops with an error.

`harvest` recomputes the selection summary of the tag from its records with the same checks and writes the manifest `docs/harvest/<name>.json`, to be committed before any blind evaluation. Without `--step` it ranks finished population lineages (role `member`, status `done`) by the selection `macro` of their final adapters (the mean over procedural families, as in Round 1; Round 2's ranking key is decided with the population protocol). With `--step S` every population slot's current lineage (following replacements) with a step-S checkpoint is ranked by the macro of `<lineage>@S`, whatever its status. A slot whose lineage was culled and whose replacement has not reached S, or which has no replacement left, is not ranked but recorded under `culled_slots`; the harvest refuses, listing each gap, if a never-culled slot lacks the step-S checkpoint or a ranked adapter lacks a complete, matching evaluation. Baselines are listed, never ranked, at every step at which they were evaluated under the tag. A run of baselines only harvests with an empty ranking and null `outlier` and `top3`.

Only `evaluate.py` opens the vault: the task layer loads vault items only with the receipt returned by `evaluate.blind_guard`. The guard refuses unless the manifest is tracked in git, identical to `HEAD`, and lists every requested adapter's content hash (over `adapter_config.json` and `adapter_model.safetensors`, both of which vLLM reads) under `ranking` or `baselines`. Round 2's rule is stricter than Round 1's: no model, the base model included, runs on a blind item before the manifest is committed, so a base-only evaluation needs the manifest too. Before any generation it appends a line to `docs/blind-ledger.md`, which notes when the vault had already been opened (time and run of the first opening); commit the ledger with the results. The guard still knows Round 1's `blind1`, whose ledger lines it reads, but the task layer no longer evaluates it.

## Context score

`context-score` measures how much of each context a member's uninstructed answers carry. For every subject — the base model's plain probe answers (`base`), its answers under each selected context (`base:<context>`), and the committed probes of the lineages and steps chosen by `--members` and `--steps` (`<lineage>@<step>`; default all) — and for every selected context, it computes, by domain, the mean over completion tokens of log p_base(token | prompt with the context) − log p_base(token | plain prompt), on the stored sampled token ids, with the frozen base model on the GPU. `--contexts` selects contexts (default all of the run's), and `--items N` a domain-stratified subset of the probe set (proportional shares by largest remainders, a seeded draw within each domain), the same items for every subject. The plain and all context prompts of a subject go through one forward-only pass, in micro-batches of four times the trainer's token budget.

Each selection of items and contexts has its own directory `runs/<name>/context_score/<N>items-<C>contexts-<hash>/` with `selection.json` (positions, uids, contexts), one cache file per subject keyed by the SHA-256 of its responses file, so that a rerun scores only new or rewritten probes, `table.csv` with the columns `subject, lineage, step, context, domain, responses, tokens, delta_sum, delta_mean` (token-weighted: `delta_sum / tokens`) for every subject scored under that selection, and `responses.csv` with the same values per scored response, for members and the base references alike: `subject, lineage, step, uid, domain, context, tokens` (completion tokens) and `delta_sum` (the response's summed log-ratio), from which analysis can resample items. The index of the design (base model 0, instructed answers 1) is computed in analysis from the `base` and `base:<context>` rows. Probe files past a lineage's committed step are skipped, and a probe file whose items are not in the base model's order is refused.

## Scaled adapters, deviation and cross-likelihood

`scaled` probes a member exaggerated in weight space. For each adapter `<lineage>@<step>` (a committed checkpoint) and factor f it writes the adapter whose update to the base model is f times the original: every LoRA B tensor times f, A and `adapter_config.json` unchanged, so that (α/r)·B·A becomes f times itself and nothing else differs. That adapter answers the run's probe set once, with the seeds of the lineage's own probe at that step, so that scaled and unscaled answers are paired draws, and the answers are scored and stored like a probe under the label `<lineage>@<step>x<f>` (f written as `%g`) in `runs/<name>/scaled/<label>/`. The summary is written last; a label already summarised is skipped, an unfinished one redone. Nothing in the members' directories changes.

`deviation` measures, on stored probe answers, how much more likely the author finds them than the base model does. Its items are the context score's: `--items N` takes the same domain-stratified positions as `context-score --items N`. Authors are the committed probes of every lineage (`<lineage>@<step>`, scored with the checkpoint of that step) and every scaled probe (scored with its scaled adapter), selected by `--members` (lineage ids or labels; scaled probes count as their lineage's) and `--steps`. Per response it writes the completion tokens and `delta_sum`, the sum over them of log p_author − log p_base; the deviation of the design in nats per token is `delta_sum / tokens` aggregated in analysis. With `--cross` and exactly one step, every selected adapter at that step and the base model score every one's answers, the base model's plain probe answers included, which gives the summed log-probability per (scorer, author, item): distinctness, authorship by likelihood and, on the diagonal minus the base row, the deviation again. Next to every sum both tables give the answer's layout tokens, those whose text (decoded alone, a special token as empty text) contains no letter or digit: whitespace, punctuation, markup and the end-of-turn token. `layout_tokens` counts them and `layout_delta_sum` or `layout_logprob_sum` sums over them alone, so that analysis can report how much of a member's deviation and of a pair's margin sits in layout. Both passes are forward-only, in micro-batches of four times the trainer's token budget. Each selection has its directory `runs/<name>/deviation/<N>items-<hash>/` with `selection.json`, one cache file per author (`<label>.json`) or per scorer and author (`cross-<step>/<scorer>--<author>.json`), keyed by the SHA-256 of the responses file and the scoring adapter's content hash, `responses.csv` with every author scored under that selection, and `cross-<step>.csv`. A cache file from before the layout columns is recomputed when its author is selected and otherwise left out of the table, like one whose answers changed.

Probe-step checkpoints keep their adapter, a PEFT directory vLLM can load (139 MB for 1.7B at rank 32), for evaluation of `<lineage>@<step>`; a light checkpoint is deleted once a newer checkpoint is committed, unless it is a clone point. ## Record schemas

Task uids and fields are the task layer's (`<source>/<item id>`; procedural instances `<family>/<dataset seed>/<index>`). All times are UTC ISO strings.

A *response record* has the task's `uid, family, domain, kind, wrapper, stratum, question`, the sample's `text` (completion without special tokens), `completion_tokens` (number of sampled ids, end-of-turn included), `finish_reason` (`stop` or `length`) and `logprob` (vLLM's summed log-probability of the sampled ids), and every field of the task layer's `Score`: `reward, correct_any, complied, channel, truncated, extracted, error`. Files built from it:

| File | One record per | Fields besides the response record |
|---|---|---|
| `rollouts/step_T.jsonl.gz` | rollout | `step` (T), `prompt` (index within the step's batch), `k` (rollout index), `return` (of the shaped reward, with the length deduction), `weight` (advantage used in the update); with taste at strength ≠ 0 also `taste_score` (s, null if not eligible) and `taste_factor`; with revisits also `revisit` (whether the prompt is a revisit) |
| `probe_responses/step_S.jsonl.gz` | probe answer | `step` (S), `token_ids` (the sampled ids) |
| `base/probe_responses.jsonl.gz`, `base/contexts/<c>.jsonl.gz` | probe answer | `step` (null), `context` (null or the context), `token_ids` |
| `scaled/<label>/probe_responses.jsonl.gz` | probe answer | `step` (the adapter's), `factor`, `token_ids` |
| `eval/<suite>/<tag>/records-*.jsonl.gz` | sample | `adapter` (label as given), `adapter_sha256` (null for base), `suite`, `sample` (index) |

`history.jsonl`, one line per update:

- seeding (`phase: "seed"`): `method`, `step` (0-based update), `time`, `completion_tokens` (mean) and `truncated` (share) of the update's samples, the trainer's statistics (`loss`, `grad_norm` before clipping, `sequences`, `tokens`, `micro_batches`, `update_s`, and on GPU `peak_alloc_gib`), and `timing` (`generate_s` of the joint generation, `batch_members`, `update_s`, and for opcd `check_s`, `publish_s`). opcd adds `kl` (the token-mean reverse KL, equal to `loss`) and `check` (as below); imitation adds `correct` (correct teacher answers) and `prompts_with_correct`, and its trainer statistics include the self-imitation fields at zero.
- amplification (`phase: "amp"`): `step`, `time`, `version` (adapter name published after the update), `reward` and `return` (means over rollouts), `reward_by_family`, `completion_tokens` (mean), `complied`, `truncated` (shares), `groups` (prompts with non-zero weights), `prompts`, the trainer's statistics (`loss` (the weighted sum), `adv_loss`, `si_loss`, `ex_loss`, `grad_norm`, `sequences` and `tokens` in any term, `adv_sequences`, `adv_tokens`, `si_sequences`, `si_tokens`, `ex_sequences`, `ex_tokens`, with replay imitation `rp_loss`, `rp_sequences`, `rp_tokens`, `micro_batches`, `update_s`, `peak_alloc_gib`), for a practising member `practice` (`shares` by source that the batch was drawn with, `averages` by source they came from, and with `reference: base` the base model's mean pass rate by source on the step's items, `base`), with taste at strength ≠ 0 `taste` (`eligible` rollouts scored; `shaped` rollouts and `groups`, both 0 when `skipped` gives the reason; `sigma`; `score_mean` and `score_sd` of s and `length_corr`, its correlation with completion tokens, over the eligible rollouts; with `residualize` the fit's `length_intercept` and `length_slope`; `adv_plain` and `adv_shaping`, the mean over all rollouts of |weight without shaping| and of |weight − weight without shaping|; `member_vs_sampler`; `taste_s`), with revisits `revisit` (`source`, `slots`, `frontier` (its size at the start of the step), `own` (the items `own` drew or would have drawn, in draw order), `revisits` (the revisited items; for `matched` aligned with `own`, null where nothing matched), `shortfall`, and the mean reward of the revisit prompts' and of the other prompts' rollouts, `reward` and `stream_reward`), `check` (`rollouts, tokens` actually re-scored, `token_mean_abs, seq_mean_abs, seq_abs_per_token`, and `first_attempt` with the failed sample's statistics when the check was repeated on the whole batch) and `timing` (`generate_s`: wall time of the rollout batch shared by `batch_members` members; `score_s, check_s, update_s, publish_s, write_s`: this member's own; `publish`: `save_s, load_s, unload_s, cleanup_s`).

`probes.jsonl` and `base/probe_summary.json` (and `base/contexts/<c>.json`, with `context`): `step` (members only), `time`, `n`, `accuracy`, `by_domain`, `by_family`, `complied`, `correct_any`, `by_wrapper` (compliance), `truncated`, `completion_tokens`, and for members `cull` (null or the reason) and `culled` (whether it was acted on).

`state.json`: `id, slot, generation, context, seed, parent` (null, or `{lineage, step}` for a clone), `status` (`new`, `active`, `done`, `culled`), `step` (updates done at the last checkpoint), `probes` (the probe summaries up to it), `cull_reason`, `replaced_by`. `practice.json`: `averages` (source → moving average after the checkpoint's step) and `drawn` (stream pool `<source>/<stratum>` → items drawn in the member's own batches). `items.jsonl.gz`: one line per item shown, in the order first shown, `uid, attempts, successes, first` (step of the first success or null), `wrapper` and `answer` (the first successful answer's wrapper and sampled ids, null unless it was recorded live within `length.free`).

`scaled/<label>/probe_summary.json`: `label, lineage, step, factor, time, source` (the checkpoint scaled), `source_sha256`, `adapter_sha256` (of the scaled adapter) and the fields of a probe summary. Deviation tables: `responses.csv` with `subject, lineage, step, factor` (empty for a member's own probe), `uid, domain, tokens, delta_sum, layout_tokens, layout_delta_sum`; `cross-<step>.csv` with `scorer, author, step, uid, domain, tokens, logprob_sum, layout_tokens, layout_logprob_sum` (`base` as scorer is the base model, as author its plain probe answers).

Evaluation `params.json`: `suite, per_family, samples, per_source`. `summary.json`: the same plus `time` and `adapters`, mapping each label to `adapter_sha256, n, n_by_family, macro` (mean of per-family accuracy over procedural families; the Round 1 harvest key), `by_family` (dataset sources included), `complied, correct_any, truncated, completion_tokens`.

Harvest manifest: `run, time, revision, tag`, `outlier` and `top3` (labels; null for a baseline-only run), `ranking` (entries `lineage, slot, context, selection_macro, adapter, sha256, rank`) and `baselines` (the same without `rank`). With `--step` also `step`, a `step` and an evaluation `label` in every entry, and `culled_slots` (entries `slot`, `culls` with each culled lineage's `lineage, step, reason`, `current` lineage and `current_step`, `status` `young` or `exhausted`). Ledger lines: `| time | vault | revision | manifest sha256 | adapters | per family x samples (per external source) | run <name>[; reuses <vault>, first opened <time> (run <name>)] |`.

## Measured costs

Qwen3-1.7B on one L20, measured on 2026-11-25. The trainer was benchmarked alone on a card (its peak adds to vLLM's fixed footprint above), on random token ids behind 300-token prompts, 64 prompts × 4 rollouts or 64 distillation sequences, LoRA rank 32, default trainer settings:

| Update | Tokens in the loss | Seconds | Peak allocated |
|---|---|---|---|
| amplification, β = 0.5, completion lengths uniform 100–4,096 (244 of 256 rollouts in a term) | 507k | 203–209 | 6.9–7.1 GiB |
| the same without shared-prefix rows | 507k | 184 | 6.8 GiB |
| amplification, β = 0.5, every rollout at 4,096 tokens (216 of 256 in a term) | 885k | 202–203 | 6.6 GiB |
| opcd, 64 completions of 4,096 tokens, teacher prompts 170 tokens longer | 262k | 93–105 | 5.1 GiB |

The peak stays at Round 1's level (6.8 GiB) because rows are capped at the token budget and the output projections are chunked; time grows with the tokens in the loss, at 2,500–4,400 trained tokens per second. At these lengths shared-prefix rows no longer pay: a prompt of 300 tokens is small beside its completions, and packed rows need a masked attention and padding (Round 1's short answers made them twice as fast). The default is kept until the census gives the real length distribution; `trainer.shared_prefix: false` changes speed only. With self-imitation most successful rollouts enter the update even when their group has no advantage, so an update costs up to the whole batch.

The end-to-end toy run (`configs/run/toy.yaml` on the Round 2 task layer, with a provisional strata table in place of the census's; one worker, KV 12G, on cards shared with other users) gave these costs. `prepare`: the 357-item probe set answered plainly and under each of the 12 contexts, 1–2.5 minutes each, 26 minutes in all. A worker spends about 6 minutes rebuilding and checking the probe set before vLLM starts (on a machine at load 55–65), and vLLM 3–5 minutes to start. opcd seeding with 32 prompts per update: generation 33–110 s, consistency check 1–4 s, update 14–25 s (13–20k tokens, peak 5.7–6.0 GiB), publish 1.3–1.6 s. Amplification of four members (16 prompts × 4 rollouts each, β = 0.5, answers 460–810 tokens on average): joint generation 77–111 s, update 12–38 s per member (28–43k tokens, 44–56 of 64 rollouts in a term, peak 6.8–7.1 GiB), consistency check 0.009–0.013 per token. A probe of 357 items: 276 s of generation for two members. An evaluation of 3 adapters on 67 selection items: 2.3 minutes of generation. The context score: one subject of the whole probe set (357 answers × 13 prompts) took about 6 minutes on a busy card. With `--items 120` and all 12 contexts (13 prompts, 1.3M tokens) it takes 84 s on an idle card, about 15,500 tokens per second, close to the card's compute limit, whatever the micro-batch size, and 87–99 s (trainer's budget: 103–135 s) or 163–165 s (170–207 s) beside other users' jobs; the larger forward-only budget helps only on busy cards. About a minute per subject therefore needs fewer prompts or items, for instance `--items 120` with the subject's own context and the placebo (3 prompts), or about 80 items with all contexts. The scores are reproducible to the bf16 noise of batching: scoring the same answers in other micro-batches changes a token's log-probability by 0.012 on average, without bias (mean signed change 4e-6), but rare near-tie tokens move by up to 1.6 nats, so a per-domain mean over a few thousand tokens moves by up to 0.004 nats.

The amplification mechanisms were measured on 2026-11-26 with one unseeded member per arm of pilot D in one worker (48 prompts × 4 rollouts at 4,096 tokens, KV 12G, on a card beside another user's 8 GB job; five updates). The joint generation for four members took 163–239 s per step while answers averaged 530–900 tokens, and the probe of four members at step 0 took 379 s. The updates of the relative-only and practice members took 25–50 s (50–107k tokens). Those with exaggeration took 47–56 s at the same lengths (80–98k tokens, 36–49k of them eligible): the eligible rollouts without advantage, the base pass and the full-vocabulary KL add about 15–20 s. The trainer's peak was 6.8–7.2 GiB in every arm, the exaggeration term adding at most 0.15 GiB, and the consistency check gave 0.007–0.016 per token. The exaggeration term's gradient grows with the member's own deviation from the base model, which RL alone multiplies several times per step at first. At weight 0.5 and γ 1 it was 3 times the advantage term's gradient after one update and 56 times after three; the exaggerating members' answers grew from 530 to 1,560 and 1,900 tokens, and one member's probe accuracy fell from 0.43 to 0.29 in five updates. At weights 0.2, 0.1 and 0.05 it passed the advantage term's within two to four updates. Its size is logged in `ex_loss`, the KL in nats per token. Practice moved the shares within five steps to 0.57–1.32 times the defaults. Scaled probes of two of pilot C's step-45 adapters at factors 1.5 and 2 took 1,829 s of generation for the four labels, because scaling lengthens the answers (to 1,500–3,600 tokens on average). With `--items 120`, `deviation` took 14–60 s per author, and `--cross` took 101–106 s per scorer for five scorers and authors.

The taste-shaped reward was measured on 2026-11-26 with three clones of pilot C's `unseeded-adv` at step 45 (strength +0.25, 0 and −0.25; 48 prompts × 4 rollouts at 4,096 tokens, KV 12G, one worker on an otherwise idle card, five updates; scratch run `runs/e3check`). Joint generation took 223–286 s per step for the three (answers of 1,090–1,270 tokens on average), a probe of the three 511–540 s, and a whole step 7.4–8.8 minutes. Of a step's 192 rollouts 88–110 were eligible and 76–104 shaped, in 25–32 groups. Scoring them took 15–18 s, and the update 66–87 s (180–225k tokens) against 41–69 s (109–175k) for the neutral clone, because groups of correct answers without advantage now enter the advantage term; the trainer's peak was 7.02–7.12 GiB in all three. The trainer's member log-probabilities agreed with the sampler's to 0.0011–0.0015 per token over every scored rollout. The score averaged 0.26–0.29 nats per token (SD 0.09–0.16 over a step's eligible rollouts), but its spread within groups, σ, was only 0.029–0.041. Shaping added a mean |advantage| of 0.12–0.21 next to 0.31–0.51 from correctness and length, and did not grow over the five steps.

Within groups the score falls with answer length (correlation with log length −0.47, about a fifth of its variance): a member's deviation sits in part of its tokens, and a longer answer dilutes it, so the reversed sign favours the longer of two correct answers and the own direction the shorter. Header level and bold, digit and code density add little (with length, 24–28% of the variance). In the most contrasting pairs of similar length both answers share the method and the member's heavily bolded markdown; they differ in presentation details (`## **Step` against `### **Step`, the opening line) and in how much of the problem's data they restate, which both models predict alike. Nothing in them separates different ways of solving. After five updates the probe accuracies were 0.424 (own), 0.498 (neutral) and 0.441 (reversed), from 0.439–0.453 at the clone point (one sample of 357 items: a standard error of about 0.026 each), compliance 0.905–0.924, mean probe answers 1,053–1,121 tokens.

The frontiers that revisits draw from were measured on 2026-11-26 on pilot C's fourteen relative-only members at step 45, with records rebuilt from their rollouts (the same 2,160 items shown to all, all but two once). A member's frontier held 593–714 items (27–33% of those shown), of mean census pass rate 0.39 against 0.45 for all shown items; the draw's weights bring the expected pass rate of an `own` revisit to 0.29. The frontier held 20% of the items the base model never solved in eight samples, 39–46% of those it solved one to four times and 6% of those it always solved. About 30% of newly shown items enter the frontier at their first visit, so 16 slots per step never run short over 45 further steps, even if no item were revisited twice. Two members' frontiers overlap with a Jaccard index of 0.29 on average (0.24–0.33 over the 91 pairs; 0.31 for the two unseeded members, which differ only by seed). Frontiers drawn independently within cells of source and census pass rate would overlap at 0.23, and two members with the same solve rate on every item at 0.37, also when each keeps its own overall level (the solve rates estimated from the other twelve members; on simulated identical members this estimate and their actual overlap agree at 0.37). Frontiers are thus far from identical and less alike than sampling alone would make two equal members.

## Known limitations

- The update is the plain on-policy policy gradient, with no importance correction for the remaining sampler–trainer mismatch (about 0.006 nats per token with the bf16 LoRA path).
- The distillation loss ignores how the member's own sampling depends on its weights (the gradient flows through the per-position distributions only), as is usual for on-policy distillation.
- The consistency check detects a wrong member, a base/adapter swap, or a prompt or scaling mismatch once the adapter differs from the base model by more than the noise; it cannot tell two consecutive versions apart, and at seeding update 0 the member is the base model. Stale weights are excluded by the version naming, not by the check.
- Sampling is seeded, but vLLM's numerics depend on batch composition, so a resumed step or a rerun reproduces samples only approximately; two clones in different batches are not bit-identical in the parts of their samples their seeds share.
- Seeding has no checkpoints; an interrupted seeding restarts from scratch.
- A clone needs its parent's first lineage to reach the clone point; with culling enabled a parent culled earlier stops the clone's worker. A clone point chosen after the parent has passed it is possible only for steps listed in `clonable_steps`.
- Shared-prefix rows are padded to the longest row of their micro-batch.
- Runs on stream version 1 (pilots B, C and D and every clone added to them) keep its defect: at 48 prompts on pilot C's pools the shared batches of steps 13 and 32 hold 49 prompts and a pool repeats an item afterwards (none between steps 33 and 100); practice batches never do. Checked on the recorded rollouts: the version-1 stream of the current code reproduces every batch that pilot C's members and clones (steps 0–89) and pilot D's members trained on.
- Practice by default follows a member's absolute reward per source, which includes how hard each source is for the base model, so part of every practising member's shares is common to all of them (pilot D). In pilot C's first 15 steps the unseeded members' training rewards per source ranged from 0.35–0.38 (MATH) to 0.52–0.57 (ProofWriter), largely in the same order for every member; at eta 4 that alone moves shares by factors of about 0.6–1.5. `reference: base` removes the base model's part, as far as the census pass rates (8 samples per item) measure it.
- The exaggeration term costs one forward pass of the base model, without gradient, over every micro-batch that holds an eligible rollout; the taste-shaped reward costs two, of the member and of the base model, over the eligible rollouts.
- The taste-shaped reward takes the score at face value: whatever makes an answer more probable to the member than to the base model per token counts as characteristic, presentation and habitual phrasing included, and with `imitate_within_free: false` (pilot E, as pilot C) long correct answers are scored too. Being a mean per token, the score falls with answer length within a group, so the own and the reversed direction also press on length in opposite senses (Measured costs); how much of a variant's change is length or presentation has to come from the analysis (deviation within and beyond typical length, the cosmetic share of authorship).
- The length-neutral taste score removes only the part of the score that is linear in log length over a step's shaped rollouts.
- An item record rebuilt from rollouts has no answers, so replay imitation acts only on items first solved after the record began to be kept live (for pilot F's clones, after step 45).
- Revisits take the place of stream prompts: at share 0.33 a revisiting member meets 32 new items per step where its plain sibling meets 48. The replaced stream items are skipped, not deferred, so that the stream positions stay shared.
- `matched` mirrors the draw `own` would make on the matched member's own record with its own seed. From the clone point on, the two arms' records differ, so their revisits are matched in source and census pass rate in distribution, not item by item with the `own` sibling's. Being outside the frontier, the matched items are mostly ones the member never solved, with some it has mastered: in the first three revisit batches drawn from `placebo-adv`'s record at step 45 their past success rate averaged 0.11–0.39 (every pair of the same source and census pass rate), where a frontier item's lies between 0.25 and 0.5 after one visit. The matched arm's revisits can therefore be expected to earn less reward and give fewer informative groups than the `own` arm's.
- The frontier counts every attempt since an item was first shown, without recency: an item stays in it until 3/4 of all its attempts have succeeded.
- Layout tokens are classified by decoding each token alone; a token that holds part of a multi-byte character decodes to a replacement character and counts as layout.
- The supervisor keeps its control files in `logs/<run directory name>/`, so clones added to an existing run share that run's `lists` and `gpus`; supervising them separately means rewriting those files (pilot C's still list its stopped heritability clones and cards outside the four allowed) or starting their workers by hand.
- The exaggeration term does not saturate: its gradient grows with the deviation it helps to produce, so at any fixed weight it comes to dominate the update once the member has moved far enough from the base model; the weight only sets when (Measured costs).
- A worker with more members than `server.max_loras` still works, but generation for the extra adapters queues.
- Commands use paths relative to the repository root and must be started there.
- The harvest manifest and the blind ledger are written but not committed by the tools.
