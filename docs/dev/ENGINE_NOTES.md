# Engine notes

Internal operating notes for the first EvoTaste engine (`evotaste/`). The build specification is `docs/dev/ENGINE_SPEC.md`; the vLLM and trainer recipes it relies on are in `docs/dev/INFRA_NOTES.md`. This file holds the commands, the run-config schema, the on-disk layout and record schemas that analysis code is written against, measured costs, and known limitations.

## Commands

All commands run from the repository root after `source scripts/env.sh`, with exactly one GPU visible. The script also sets `PYTHONHASHSEED=0`, which child processes inherit: some reasoning-gym generators iterate sets of strings, so an instance would otherwise differ between processes, and `evotaste.tasks` refuses to import under any other value. Pick a GPU whose `memory.used` is below 500 MiB immediately before launching and pin it with `CUDA_VISIBLE_DEVICES`. Each command that needs generation starts its own vLLM server (1–4 minutes with warm compile caches) and stops it on exit, including on SIGTERM; the server also receives SIGTERM if its parent is killed with SIGKILL. `--attach http://127.0.0.1:<port>` makes a command use an already running server of the same model instead (development only; the server must have been started with runtime LoRA updating, see `scripts/dev/serve_vllm.sh`).

| Step | Command |
|---|---|
| Assign suites (once per project) | `python scripts/make_suites.py` (writes `configs/suites.yaml`) |
| Prepare a run | `CUDA_VISIBLE_DEVICES=<g> python -m evotaste.worker prepare configs/run/<name>.yaml` |
| Start a worker | `CUDA_VISIBLE_DEVICES=<g> nohup python -m evotaste.worker run runs/<name> --members m00,m01,m02 [--checkpoint-every 5] [--kv-cache 12G --gpu-memory-utilization 0.45] [--max-loras 10] > /dev/null 2>> logs/<name>/stderr-gpu<g>.log &` |
| Resume | the same `run` command again |
| Fork after seeding | `python -m evotaste.worker fork runs/<source> configs/run/<new>.yaml [--dry-run]` |
| Evaluate | `CUDA_VISIBLE_DEVICES=<g> python -m evotaste.evaluate run runs/<name> --suite selection --adapters base,m00,m01 --per-family 50 [--per-source 500] [--samples 1] [--shard i/n] [--tag t]` |
| Harvest | `python -m evotaste.evaluate harvest runs/<name> --tag n50x1 [--step S]`, then commit `docs/harvest/<name>.json` |

`prepare` freezes the run: it copies the config into `runs/<name>/config.yaml` (with `suites` and `scaffolds` pointing at copies of `configs/suites.yaml` and `configs/scaffolds.yaml` placed next to it), checks that every probe and seeding-pool gold answer earns reward 1, lets the base model answer the seeding pool once per teacher condition (plain, and each scaffold named by a member), and answers the probe set with the base model. It is idempotent and refuses to run if the run directory exists with a different config, suites or scaffolds. Workers only read these shared artefacts and refuse to start on an unprepared run, or when the probe set rebuilt by the current code differs from the one the base model answered at prepare time (a run prepared before a change of task instances cannot be continued), so several workers on different GPUs can share one run directory: give each a disjoint `--members` list. An exclusive lock per member slot (`runs/<name>/locks/<slot>.lock`) makes a second worker on the same member exit immediately.

`fork` creates a prepared run `runs/<new>` that shares the source run's seeding: it copies the seeding pools and base probe answers, and for every member id present in both configs with the same arm, scaffold, seed and effective seeding settings whose source lineage has a committed step-0 checkpoint, it copies that checkpoint (the adapter after seeding, no optimizer state), the seeding history and the step-0 probe, and writes a state at amplification step 0. Other members seed normally. It refuses unless model, run seed, `lora`, `seeding`, `probes`, `trainer` and the suites and scaffolds content are identical; amplification, culling, server and member overrides of those may differ. The source may be live: files are copied, never moved or linked, and a member still seeding counts as having no checkpoint. `prepared.json` of the fork records `fork: {source, source_revision, members}`. `--dry-run` prints the plan and creates nothing. A forked member's amplification is the same computation as an unforked one's from step 0: the same fp32 adapter, a fresh AdamW state in both cases, the same training stream; only adapter version names (pid and counter) and the unseeded rollout sampling differ, as between any two runs.

A worker advances its members until each has finished its steps or its slot is exhausted. Killing it at any point and starting the same command again resumes every member from its last checkpoint. Besides the checkpoint written at every probe, `--checkpoint-every N` (an operational setting, default `probes.every`; it does not alter the frozen run) writes a light checkpoint without a probe every N steps, so a death costs at most N steps. A CUDA out-of-memory error in the trainer (a co-tenant took memory on the shared card) is retried from clean state: cached memory is released, the card's per-process memory is logged, and the same member step (consistency check or update; a seeding update likewise) is tried again after 100 s, up to 10 attempts (about 15 minutes) before the error ends the worker. A retry computes exactly the update an uninterrupted run would have: same rollouts, and the member's weights and optimizer state are copied into the trainer and back only when an update has completed. A failure inside vLLM still ends the worker at once. A worker limits its torch CPU threads to 4: its CPU work is small, and with torch's default of one OpenMP thread per core (96 here) the adapter's dtype conversion before each publish stalled for 10–80 s whenever several workers' parallel regions met on the loaded machine (eight concurrent processes converting the same adapter: 0.016 s median with 4 threads each, no progress in minutes with 96). Logs go to `logs/<name>/`: one file per command invocation (`prepare-…`, `fork-…`, `worker-<members>-…`, `eval-<suite>-…`) and one vLLM log per server. Whatever ends a command is written to its own log before it exits: the full traceback of an exception (`terminated by an exception`, or `exiting: <message>` for a refusal), or `received SIGTERM` / `received SIGINT` followed by `stopped by …` for a deliberate stop; a CUDA out-of-memory error in a worker also logs `nvidia-smi`'s per-process GPU memory before vLLM is stopped. Keep stderr anyway (as in the launch command above): an interpreter-level failure before logging starts can only appear there.

`evaluate run` accepts `base`, a lineage id (its last checkpoint, which is the final adapter of a finished lineage) or `<lineage>@<step>`. It takes `--per-family` instances of every procedural family and `--per-source` items (default: the `--per-family` value; a larger value than a part holds takes the whole part) of every external source. Both are recorded in `params.json` (`suite, per_family, samples, per_source`; files written before `per_source` existed mean `per_source = per_family`), and the default tag `n<per-family>x<samples>` gains `s<per-source>` when the two differ. External parts after the question-text split: GSM8K train 7473 (foundation); GSM8K test 657 / 662 and MATH-500 249 / 251 (blind1 / blind2); MMLU-Pro 4027 / 4081 / 3919 (foundation / blind1 / blind2). Sharding splits the (adapter, instance) job list; each shard writes its own record file. After each invocation the summary is recomputed over all record files of the tag and written only if every label comes from a single adapter (one hash across all files) and covers the requested grid exactly, every (family, instance, sample) once; while records are only missing (shards still running) the summary is removed and a warning logged, and any other inconsistency stops with an error. Blind vaults get the same check. On `blind1` or `blind2` the evaluator first calls the blind guard (below). Never evaluate a trained adapter on a blind vault outside the protocol's final comparisons.

## Run configuration

A run config is YAML; unknown keys and wrongly typed values are errors. `worker run`, `worker prepare` and `evaluate run` accept `--kv-cache`, `--max-loras` and `--gpu-memory-utilization`, which replace `server.kv_cache`, `server.max_loras` and `server.gpu_memory_utilization` for that process only (logged at start; the frozen config is unchanged). They change the memory footprint and the speed, never results. Measured vLLM footprints for Qwen3-1.7B at rank 32 are about the KV budget plus 6.8 GiB (26.8 GiB at 20G, 18.9 GiB at 12G, so about 14.9 GiB at 8G; two more LoRA slots add about 0.15 GiB), and a worker's trainer holds 8.7–9 GiB (12.2 GiB for the wide baseline's larger batches) whatever the number of members, since only the active member is on the GPU. A worker therefore needs about 28–31 GiB at 12G and 24–27 GiB at 8G of the card's 44.4 GiB. Lower `--gpu-memory-utilization` with the KV budget (about 0.45 at 12G, 0.35 at 8G), or vLLM's startup check fails beside a co-tenant. Nothing else sizes itself from the KV budget: the client keeps up to 512 requests in flight and the trainer's token budget is independent; a small cache only makes vLLM pause and recompute sequences when answers are long. Defaults are those of `docs/design/protocol.md` and the spec. Section by section:

| Key | Default | Meaning |
|---|---|---|
| `name` | required | run directory `runs/<name>/` and log directory `logs/<name>/` |
| `model` | required | Hugging Face id, e.g. `Qwen/Qwen3-1.7B` |
| `seed` | required | seed of the training stream and the seeding pool (probe and evaluation sets do not depend on it) |
| `suites`, `scaffolds` | `configs/suites.yaml`, `configs/scaffolds.yaml` | sources copied at prepare time |
| `server.kv_cache` | `20G` | vLLM `--kv-cache-memory-bytes` |
| `server.gpu_memory_utilization` | 0.65 | with a fixed KV budget only a startup check (free memory ≥ fraction × card); vLLM's default 0.92 fails whenever the trainer, loading in parallel, or anyone else holds memory |
| `server.max_num_seqs`, `server.max_num_batched_tokens` | 512, 8192 | vLLM scheduler limits |
| `server.max_loras` | 8 | adapters that can share a batch; raise it if a worker has more members |
| `lora.rank`, `lora.alpha` | 32, 64 | LoRA on all seven projection types |
| `trainer.token_budget` | 8192 | padded tokens per micro-batch (rows × longest row) |
| `trainer.shared_prefix` | true | one row per prompt holding the prompt once and all its completions |
| `trainer.grad_checkpointing` | true | needed to fit next to vLLM |
| `trainer.max_grad_norm`, `trainer.weight_decay` | 1.0, 0.0 | AdamW (betas 0.9/0.999, eps 1e-8) |
| `trainer.check_tokens`, `trainer.check_rollouts` | 3000, 8 | minimum completion tokens and rollouts re-scored by the trainer before every update |
| `seeding.pool_prompts`, `seeding.samples`, `seeding.max_tokens` | 1536, 4, 640 | teacher sampling of the seeding pool (shared per teacher, not overridable per member) |
| `seeding.steps`, `seeding.batch`, `seeding.lr` | 30, 64, 1e-5 | positive warm-up updates |
| `seeding.perturb_std` | 0.01 | perturbation arm: LoRA B drawn from N(0, σ) |
| `amplification.steps`, `.prompts`, `.rollouts`, `.max_tokens`, `.lr` | 300, 64, 4, 640, 1e-5 | group updates; sampling is always at temperature 1, top-p 1 |
| `amplification.truncation_penalty` | 0.0 | λ ≥ 0: group weights from the shaped return reward − λ·truncated (see below) |
| `probes.every` | 20 | probe and checkpoint every E steps, and after the last step |
| `probes.train_per_family`, `.selection_per_family`, `.foundation_per_source` | 8, 12, 150 | probe set sizes |
| `probes.max_tokens` | 640 | also used by `evaluate` |
| `culling.grace` | 40 | no culling at probes before this step |
| `culling.max_replacements` | 2 | new lineages per slot before the slot is given up |
| `members` | required | list of `{id, arm, seed, scaffold?, overrides?, role?}`; `role` is `member` (default) or `baseline` |

`arm` is `plain`, `scaffold` (requires `scaffold`, a name from `control` or `scaffolds` in the scaffolds file, e.g. `cot` or `verify`) or `perturb`. Member ids use letters, digits, `_` and `-`. `overrides` may replace keys of `seeding` (except the pool keys), `amplification` and `culling` for one member; the long baseline is `{role: baseline, overrides: {amplification: {steps: <N × steps>}}}` and the wide one `{role: baseline, overrides: {amplification: {prompts: <N × 64>}}}`. A `baseline` member trains, probes and evaluates like any other but is never ranked by the harvest. Batch b of a member with `prompts: P` is items `[bP, (b+1)P)` of the run's training stream. `configs/run/toy.yaml` is the example.

## Mechanisms worth knowing

Instances are pure functions of (stream key, family, occurrence): stream item j of the training stream (`train/<seed>`) or seeding pool (`seedpool/<seed>`) takes its family from a seeded permutation of the train families per block of `len(train)` items, so every family appears once per block. A training or seeding item whose question equals a train-test probe question is redrawn deterministically (up to 16 draws). Probe sets use stream key `probe`, evaluation sets `eval`; neither depends on the run seed. Every position owns 16 fixed draws: a draw whose generator raises is skipped in every stream, and in probe and evaluation sets (not in the training stream or the seeding pool, which stay exactly as members trained on them) so is a draw whose gold answer its own scorer rejects; external items with such a gold answer are replaced by the next item of the part's order. Each skip is logged once per process, sets without such draws are unchanged, and `check_gold` remains the final guard. For main1-tp's sets: train at 100 per family redraws one instance (`base_conversion/1039087889/832`), selection at 200/300 and blind1/blind2 at 200/650 none. External items are split by a seeded hash of their normalised question text, so identical questions under different ids land in the same part in every source: GSM8K train is foundation; MMLU-Pro is split three ways into foundation, blind1 and blind2; GSM8K test and MATH-500 two ways into blind1 and blind2. The five MMLU-Pro items that repeat a MATH-500 problem are dropped. GSM8K train, GSM8K test and MATH-500 share no question text. Probes take the first items of the foundation order, evaluation takes the last ones.

The reward is 1 if the completion stopped by itself, contains an `<answer>…</answer>` span (the last one counts), and the family's scorer gives at least 0.999; otherwise 0. Scorers run in a pool of eight persistent scorer processes per engine process (about 4,500 answers per second): a scorer exception scores 0 with its message in `score_error`, and a call still running after 10 s of wall time (sympy on `1e999999999` would run for minutes inside C code, where no signal reaches it) is ended by killing its process, scores 0 with `score_error` `timeout`, and the process is replaced. `scripts/make_suites.py` keeps only families whose scorer, on 64 fresh instances, gives reward 1 to the wrapped gold answer and 0 to an empty or junk answer, and, checked after the deal so that no other family changes suite, rewards none of the constants 0, 1, nan and inf, no strict prefix that changes the gold answer (same numbers within 1%, or same letters and digits, count as unchanged), and the gold answer between two other gold answers on fewer than half of the instances (this removed `coin_flip`, `complex_arithmetic` and `time_intervals`). External scorers: GSM8K requires exactly one number equal to the gold number; MATH-500 uses math-verify equivalence; MMLU-Pro requires the answer to start with the gold option letter.

The update minimises −Σᵢ wᵢ Σₜ log π(yᵢₜ) / Σᵢ |yᵢ| over sequences with wᵢ ≠ 0, end-of-turn token included, with one AdamW step and gradient clipping. Group weights are (r − mean) / (population std + 1e-6) within each prompt's rollouts, zero for groups with identical rewards. With `truncation_penalty` λ > 0, r is the shaped return reward − λ·truncated instead (λ = 1: correct 1, wrong but finished 0, cut off at `max_tokens` −1), standardised the same way and zero when identical; it gives a signal against running into the cap on prompts that a member never solves. Only the weights change: recorded rewards, accuracies, probes, culling and evaluation stay on the binary reward, and with λ = 0 the weights are exactly the reward-based ones; a step without any non-zero weight leaves the weights and the optimizer untouched. Amplification starts from a fresh AdamW state. The trainer scores exactly the sampled token ids behind exactly the prompt ids sent to vLLM. Each adapter version is saved in bf16 to a new directory under `/dev/shm/evotaste/<run>/<pid>/` and loaded under a new name `<lineage>@<pid>-<counter>`; the previous version is then unloaded and its directory removed.

Before every update the worker re-scores part of the step's rollouts with the trainer and compares with vLLM's log-probabilities: the first rollout of each prompt, then the second of each, and so on, until at least `check_tokens` completion tokens and `check_rollouts` rollouts are covered (all rollouts if the batch is smaller). The sample fails if the per-token mean |Δ| exceeds 0.04 or Σ|ΔΣ| / Σ tokens exceeds 0.015; a failed sample is repeated once on all rollouts of the step (both results logged), and only a failure there stops the worker with `ConsistencyError`. A wrong, stale or swapped adapter shifts every token and fails both; an isolated bf16 near-tie token (about 2–3 nats) cannot, whereas the former fixed sample of 8 rollouts covered only 120–200 tokens for members with terse answers, where one such token exceeded 0.015. Measured with the engine's own code (Qwen3-1.7B, random adapter, 128 rollouts of up to 640 tokens): 0.0057 and 0.0022 with the right adapter; 0.12 and 0.073 when the base model is served instead of the adapter or the reverse.

A member is culled at a probe at step ≥ `grace` (never at step 0) if fewer than half of its probe answers are parseable, more than half are truncated, its foundation accuracy is below half the base model's, or its train-test accuracy is below the base model's at this probe and at the previous probe at step ≥ `grace`. The culled lineage keeps its checkpoint; slot `s` continues with lineage `s~k` (k = 1, 2, …), seed `stable_seed("lineage", <slot seed>, k)`, which starts from seeding and runs the full course.

## On-disk layout

```
runs/<name>/
  config.yaml, suites.yaml, scaffolds.yaml   frozen at prepare time
  prepared.json                              {time, revision, teachers, fork?: {source, source_revision, members}}
  seeding/<teacher>.jsonl.gz, <teacher>.json teacher = plain or a scaffold name
  base/probe_responses.jsonl.gz, probe_summary.json
  members/<lineage>/
    state.json, history.jsonl, probes.jsonl
    rollouts/step_TTTTTT.jsonl.gz            amplification step T (0-based)
    probe_responses/step_SSSSSS.jsonl.gz     probe after S updates (S = 0: after seeding)
    checkpoints/step_SSSSSS/                 adapter_config.json, adapter_model.safetensors (fp32), optimizer.pt
  eval/<suite>/<tag>/                        params.json, records-<key>-<i>of<n>.jsonl.gz, summary.json
  locks/<slot>.lock
docs/harvest/<name>.json                     harvest manifest (tracked)
docs/blind-ledger.md                         blind ledger (tracked)
```

Probe-step checkpoints keep their adapter, a PEFT directory vLLM can load (139 MB for 1.7B at rank 32), for final evaluation of `<lineage>@<step>`; a light checkpoint is deleted once a newer checkpoint is committed. Only the newest checkpoint keeps `optimizer.pt` (278 MB; absent at step 0, where amplification starts with a fresh optimizer). Both kinds have the same files, and old and new engine versions resume from either. `state.json` is rewritten only after a checkpoint is complete and is the resume point: on restart, history lines of amplification steps ≥ S, probe lines and files after S, rollout files of steps ≥ S and unfinished checkpoint directories are deleted, so redone steps replace their old records. A lineage without a checkpoint (status `new`) restarts from seeding with its directory cleared.

## Record schemas

Task uids are `<family>/<dataset seed>/<index>` for reasoning-gym instances (regenerate with `evotaste.tasks.procedural_task(family, seed, index)`, which also seeds the module-level `random` that `list_functions` draws from) and `<source>/<item id>` for external items (GSM8K: row index in the split; MATH-500: `unique_id`; MMLU-Pro: `question_id`). All times are UTC ISO strings.

A *response record* has the fields `uid, family, question, answer` (gold, as text), `text` (completion text without special tokens), `completion_tokens` (sampled ids including the end-of-turn token), `finish_reason` (`stop` or `length`), `extracted` (content of the last answer span or null), `score` (raw scorer output; 0 when not scored), `reward` (0 or 1), `parsed`, `truncated`, `score_error` (null or message) and `logprob` (vLLM's summed log-probability of the sampled ids). Files built from it:

| File | One record per | Fields besides the response record |
|---|---|---|
| `rollouts/step_T.jsonl.gz` | rollout | `step` (T), `prompt` (index within the step's batch), `k` (rollout index), `weight` (group weight used in the update) |
| `probe_responses/step_S.jsonl.gz`, `base/probe_responses.jsonl.gz` | probe answer | `step` (S; null for the base model), `suite` (`train`, `selection` or `foundation`) |
| `eval/<suite>/<tag>/records-*.jsonl.gz` | sample | `adapter` (label as given), `adapter_sha256` (SHA-256 over `adapter_config.json` and `adapter_model.safetensors`; null for base), `suite`, `sample` (index) |

`history.jsonl`, one line per update:

- seeding (`phase: "seed"`): `step` (0-based warm-up update), `time`, `loss`, `grad_norm` (before clipping), `sequences`, `tokens` (completion tokens in the loss), `micro_batches`, `update_s`.
- amplification (`phase: "amp"`): the same plus `version` (adapter name published after the update), `reward` (mean over rollouts), `return` (mean shaped return; present only when `truncation_penalty` > 0, otherwise it equals `reward`), `reward_by_family`, `completion_tokens` (mean), `parsed`, `truncated` (fractions), `groups` (prompts with non-identical rewards), `prompts`, `check` (`rollouts, tokens` actually re-scored, `token_mean_abs, seq_mean_abs, seq_abs_per_token`, and `first_attempt` with the failed sample's statistics when the check was repeated on the whole batch) and `timing` (`generate_s`: wall time of the rollout batch shared by `batch_members` members; `score_s, check_s, update_s, publish_s, write_s`: this member's own; `publish`: `save_s, load_s, unload_s, cleanup_s`, the parts of `publish_s`).

`probes.jsonl` and `base/probe_summary.json`: `step` (members only), `time`, `n`, `accuracy` (`train`, `selection`, `foundation`; each the mean over families of the family's accuracy), `by_family`, `parsed`, `truncated`, `completion_tokens`, and for members `cull` (null or the reason).

`state.json`: `id, slot, generation, arm, scaffold, seed`, `status` (`new`, `active`, `done`, `culled`), `step` (updates done at the last checkpoint), `probes` (the probe summaries up to it), `cull_reason`, `replaced_by`.

Seeding pool records (`seeding/<teacher>.jsonl.gz`, correct and stopped samples only): `uid, family, prompt_ids` (the plain prompt the member trains on), `completion_ids, text, teacher_logprob`. The summary `<teacher>.json` holds `teacher, time, generate_s, prompts, samples, correct, prompts_with_correct, by_family`.

Evaluation `summary.json`: `time, suite, per_family, samples, per_source` and `adapters` mapping each label to `adapter_sha256, n, n_by_family, macro` (mean of per-family accuracy over procedural families; the harvest key on the selection suite), `by_family` (external sources included), `parsed, truncated, completion_tokens`.

## Blind guard and harvest

Only `evaluate.py` opens a blind vault: the `Suites` class used by workers never reads the blind lists, and `tasks.blind_suite` and `external.items(..., part="blind1"|"blind2")` require the receipt returned by `evaluate.blind_guard`. The guard refuses unless `docs/harvest/<run>.json` is tracked in git, identical to `HEAD`, and lists every requested adapter's content hash (over `adapter_config.json` and `adapter_model.safetensors`, both of which vLLM reads). The base model is allowed without a manifest (calibration). Before returning, the guard appends `| time | vault | revision | manifest sha256 | adapters | per family x samples | run |` to `docs/blind-ledger.md`; commit the ledger with the results.

With `--step S` the harvest instead follows the protocol's harvest rule: every population slot's current lineage (following replacements) that has a step-S checkpoint is ranked by the selection macro of that adapter, evaluated under the tag as `<lineage>@S` (status `done` is not needed). A slot whose lineage was culled and whose replacement has not reached S, or which has no replacement left, is not ranked and is recorded under `culled_slots` (`slot`, `culls` with each culled lineage's `lineage`, `step` and `reason`, `current` lineage and `current_step`, `status` `young` or `exhausted`). The harvest refuses, listing each gap, if a never-culled slot has no step-S checkpoint or any ranked adapter lacks a complete, matching evaluation, and prints the accounting (ranked, culled with a young replacement, exhausted). In `evaluate run --adapters`, `population@S` stands for exactly the labels such a harvest ranks (it fails the same way for a never-culled slot without the checkpoint), e.g. `--adapters base,population@60,wide-cot@60,long-cot@60,long-cot@120`; the expansion is the same in every shard. Baselines are listed at every step at which they were evaluated under the tag. The manifest then also records `step`, each entry its `step` and evaluation `label`, and `outlier`/`top3` are labels (`<lineage>@S`). Without `--step`: `harvest` recomputes the selection summary of the given tag from its records with the same checks, then ranks population lineages (role `member`) with status `done` by `macro` (every finished lineage must have been evaluated with its final adapter) and writes `{run, time, revision, tag, outlier, top3, ranking: [{lineage, slot, arm, scaffold, selection_macro, adapter, sha256, rank}], baselines: [{lineage, slot, arm, scaffold, selection_macro, adapter, sha256}]}`. Baselines are never ranked or named outlier; the blind guard accepts hashes from `ranking` and `baselines`.

## Measured costs

Qwen3-1.7B on one L20 next to a resident vLLM server (KV 20G), no co-tenant on the card. The update benchmark (`scripts/bench_update.py`) uses one realistic amplification batch: the base model's 64 prompts × 4 rollouts on the first training step (prompts 273 tokens on average, completions 83 on average and at most 640), with every sequence given a non-zero weight so that all 256 enter the update.

| Update path | Seconds | Peak allocated |
|---|---|---|
| full fp32 logits over whole padded sequences, micro-batch 4 (8 runs out of memory), fp32 LoRA matmuls | 27.0 | 10.9 GiB |
| completion-only LM head, length-sorted 8192-token micro-batches, bf16 LoRA matmuls | 19.0 | 6.8 GiB |
| the same with shared-prefix rows (default) | 9.9 | 6.8 GiB |

Along the way: with fp32 LoRA matmuls and a 16384-token budget the engine's plain path took 27.2 s and the shared-prefix path 15.5 s; bf16 LoRA matmuls brought the latter to 12.6 s and the smaller budget (less padding) to 9.9 s. Budgets of 4096 and 6144 tokens measured 8.4–10.5 s, within noise of 8192. Without gradient checkpointing even a 4096-token budget runs out of memory next to vLLM. The bf16 LoRA path also agrees better with vLLM (per-token mean |Δ| 0.0057 against 0.014 with fp32 LoRA matmuls).

A default-size run with three members on one GPU (plain, verify scaffold, perturbation; 64 prompts × 4 rollouts, at most 640 tokens) spent, in its first amplification steps, 17–20 s on the joint rollout batch and per member 2.2–4.8 s on the update (only 5–15 of 64 groups had mixed rewards, so 20–60 sequences entered it), 0.2–0.5 s on the consistency check and 0.25–0.4 s on publishing: about 30 s per round, or 10 s per member step. Preparing the seeding pool took 164 s per teacher (1536 prompts × 4 samples; 17% of the prompts had a correct plain sample, 27% with the verify scaffold), the warm-up 5–6.5 s per positive update of 64 sequences (2.5–3.3 minutes per member), and a probe of three members (824 prompts each) about 50 s. The trainer process peaked at 10.7 GiB in `nvidia-smi` beside vLLM's 27.4 GiB.

## Known limitations

- The update is the plain on-policy policy gradient of the spec, with no importance correction for the remaining sampler–trainer mismatch (about 0.006 nats per token with the bf16 LoRA path).
- The consistency check detects a wrong member, a base/adapter swap, or a prompt or scaling mismatch once the adapter differs from the base model by more than the noise; it cannot tell two consecutive versions apart. Stale weights are excluded by the version naming, not by the check.
- Rollout sampling is not seeded, so a resumed step draws new rollouts. An interrupted seeding restarts from scratch (seeding has no checkpoints).
- Only training and seeding items are kept disjoint from the train-test probe. For families with tiny instance spaces, evaluation instances of the train suite can coincide with training prompts, and selection evaluation and probe instances can coincide.
- Shared-prefix rows are padded to the longest row of their micro-batch (about 85% useful tokens at the default budget); packing several rows per lane would need block-sparse attention.
- A worker with more members than `server.max_loras` still works, but generation for the extra adapters queues.
- Commands use paths relative to the repository root and must be started there.
- The harvest manifest and the blind ledger are written but not committed by the tools.
